# Tomoru 评测

[English](README.md)

用真实视频评测 Tomoru 的整条流程（识别 → 断句 → 抢先翻译 → 翻译），回答一个问题：**在尽量短的时间里，字幕和译文的质量有多好**。英、日、韩、中四种语言，覆盖用户常用的场景。每个用例是 YouTube 视频里的一段（多数 5 分钟），标准答案是视频自带的人工字幕和人工译文。

## 跑分

```sh
cd app
go run ./cmd/tomoru-bench -asr sensevoice -mt cloud -max 120 -case zh-talk-yixi,en-talk-ted,ja-anime-pv,ko-variety-runningman   # 快速集，2 分钟
go run ./cmd/tomoru-bench -asr apple -mt cloud -j 10              # 有标准答案的全部 29 段，约 20 分钟
go run ./cmd/tomoru-bench -mt local-2b -mt-only                     # 只测翻译：直接翻译人工字幕原文
cd .. && uv run bench/score.py apple_cloud_1017-1030 sensevoice_cloud_1017-1100   # 打分、并排对比
```

- **快速集**用于日常检查（重构、小的行为改动）：每种语言一段有标准答案的，只跑前 2 分钟。只有真的需要看数字时才跑全量：加新模型、断句或性能有大的改动。对比改动时，用同样的用例、换一个 `-name` 先跑一遍改动前的。
- 引擎用 `listen --file` 按原速“播放”每段录音，不用外放，也不需要录音权限；session 和 app 里的完全一样（断句、抢先翻译都开着）。所以每段要跑满它的时长，`-j` 决定同时跑几段。
- `-asr`：`apple`、`sensevoice`、`qwen3-asr-1.7b`、`qwen-cloud[:模型]`（读 `DASHSCOPE_API_KEY`，按时长计费）、`openai[:模型]`（实时转写；填 `gpt-live-transcribe` 以外的模型时走转写接口；读 `OPENAI_API_KEY`，兼容服务另读 `OPENAI_BASE_URL`；按时长计费）。`-mt`：`cloud`、`local-2b`、`local-9b`，或 `chat` 加 `-mt-url`、`-mt-model`（key 读 `MT_API_KEY`）。
- 结果在 `runs/<名字>/`（不进仓库）：每段一个 JSON，记下字幕每一次变化的时间和内容；`score.py` 写出 `score.md`。同名再跑会把新的段并进去，可以分批跑。
- 本地引擎同时跑太多段会互相抢 CPU，延迟变差：SenseVoice 建议 `-j 6` 以内，本地翻译模型 `-j 1`。

## 指标

时间都从**这个字被说出来**算起。说出来的时刻取自人工字幕：每条字幕按字数平均分配时间；字幕条通常一直显示到下一条开始，所以结束时间按这段视频的正常语速收紧。字幕本身的时间误差约 ±0.3 s，延迟主要用来比较不同配置。

| 指标 | 含义 |
|---|---|
| 错误率% | 识别错误率：英语按词，中日韩按字（混在中文里的英文按词），(替换 + 漏 + 多) ÷ 标准答案长度。比较前统一大小写、繁简、数字写法（二十一 = 21），去掉标点和 [音乐]、(笑) 之类的标注 |
| 漏% / 多% | 错误率里漏掉的字、多出来的字 |
| 静处乱字/分 | 多出来的字里，人声检测说前 4 秒都没人说话的：把音乐、噪音识别成了字。有人说话、只是字幕没收的（如预告片里没上字幕的台词）不算 |
| 上屏 p50 / p90 | 一个字从说出来到**以正确的样子**出现在屏幕上（还没定稿的灰色部分也算），一半 / 九成的字在多少秒内 |
| 定稿 p50 | 一个字从说出来到它所在的那句定稿（不再变） |
| 见译文 p50 / p90 | 一句话说完到能看到它的译文：定稿时带着抢先翻译的大意，或者完整译文开始出现，取早的 |
| 全译文 p50 | 一句话说完到完整译文全部出来 |
| chrF | 译文和人工译文的相似度（字符 n-gram F 值，0–100，中日韩不用分词）。用于同时有原文参考字幕和人工译文的 14 段。不同目标语言的分数不能互相比，只比同一批用例上的不同配置 |
| 改写% | 屏幕上出现过、后来被擦掉或改掉的字，占最终字数的百分比：每次画面变化时，把前后两个画面逐字对齐，数被删掉、被替换的字（只是在后面接着出字不算）。超过 100 表示平均每个字被改过不止一次 |
| 长行% / 碎行% | 每句的长度：超过两行（约 45 个汉字或 90 个字母）的、不到 3 个字（英语 2 个词）的 |
| CPU s/分 | 每分钟音频，Tomoru 自己和它启动的进程（引擎、tomoru-asr、llama-server）用了多少 CPU 秒。Apple 的识别在系统服务里跑，不算在内 |
| 每句秒 | 只测翻译时，翻译一句的耗时中位数 |

“只测翻译”（`-mt-only`）把人工字幕原文按句子交给翻译模型，和正常跑分的 chrF 对比，就能看出整条流程里有多少损失来自识别和断句。

## 文件

- `cases.tsv`：用例清单。一行一段：语言、场景、视频 ID、起止时间、标准答案用哪条字幕（`ref`）、有哪些人工译文（`tgt`）、备注。
- `fetch.py`：按清单下载到 `media/`。只用上传者提供的字幕，不用 YouTube 自动生成的字幕。
- `media/`：下载结果，不进仓库（视频和字幕版权属于原作者）。

```sh
python3 bench/fetch.py --list                                   # 各场景、各语言有几段
YTDLP="uvx --from yt-dlp yt-dlp" python3 bench/fetch.py --cookies-from-browser chrome
python3 bench/fetch.py --cookies-from-browser chrome zh-talk-yixi   # 只下这一段
```

YouTube 会把没登录的请求当成机器人拦下来，所以要用 `--cookies-from-browser` 借用浏览器里的登录状态。系统里的 yt-dlp 太旧时，用 `YTDLP` 指定最新版。

每段得到：

| 文件 | 内容 |
|---|---|
| `<id>.wav` | 这一段音频，16 kHz 单声道，可以直接给 `TOMORU_E2E` 播放 |
| `<id>.ref.srt` / `.ref.txt` | 本语言的人工字幕，裁到这一段，时间从 0 开始 |
| `<id>.<lang>.srt` | 人工译文（TED、Kurzgesagt、Apple 发布会等有），用来给翻译打分 |

## 场景

| 场景 | 说明 | 难点 |
|---|---|---|
| `talk` | TED、TEDx、一席等演讲 | 基准：一个人、有稿子 |
| `science` | 科普动画（Kurzgesagt） | 背景音乐不断 |
| `lecture` | 课程、讲座 | 术语多，中文课里大量英文术语；教室混响 |
| `news` | 新闻 | 语速快 |
| `podcast` | 播客、对谈 | 两三个人抢话 |
| `keynote` | 发布会 | 产品名，背景音乐，会场混响 |
| `street` | 街头采访 | 户外噪音、即兴口语 |
| `variety` | 综艺、脱口秀 | 很多人同时说、笑声、音效 |
| `drama` / `anime` | 影视预告、动画 PV | 配乐和音效盖过台词，情绪化 |
| `music` | MV、现场演唱 | 唱歌本身难识别；重点看会不会把伴奏识别成一堆乱码 |
| `live` | 直播、VTuber | 口语快、读弹幕、多人连麦 |
| `game` | 游戏实况 | 游戏音效、自言自语 |

## 还没有标准答案的用例（`ref` 为 `todo`）

直播、游戏实况、日韩中新闻、韩中影视剧等找不到人工字幕：要么没有字幕，要么字幕压在画面里（硬字幕）导不出来。这些段先只下音频，标准答案的做法：用最好的识别（云端 Qwen ASR 或 Whisper large）转写一遍，再人工逐句校对，存成 `media/<id>.ref.srt`，然后把 `ref` 改成 `manual`。歌词类直接用官方歌词，时间可以不准。

## 注意

- 人工字幕不一定逐字：有的会删掉口头禅、重复、语气词，有的按阅读习惯改写。打分前要统一标点和数字写法，分数主要用来比较不同引擎，不要看绝对值。
- TED 译文开头有一行译者署名，不是台词。
- 中英双语字幕（如雷军的发布会）里的英文行或英文字幕条会被去掉，只留中文。
- 同一个 Kurzgesagt 视频有英语和日语两个版本（`en-science-kurz` 和 `ja-science-kurz`），可以拿来对比不同语言的表现。
- 字幕结束得比视频早、后面却还有人说话时，`score.py` 会提示：后面的字都会被算成“多”，要把用例的结束时间往前改。

## 基线（2026-10-17，M5，29 段 137 分钟）

| 配置 | 错误率% | 上屏 p50 / p90 | 定稿 p50 | 见译文 p50 / p90 | 全译文 p50 | chrF | 改写% | CPU s/分 |
|---|---|---|---|---|---|---|---|---|
| Apple + 云端翻译 | 14.1 | 0.77 / 1.68 | 2.59 | 1.15 / 2.53 | 1.34 | 34.6 | 5 | 1.3* |
| SenseVoice + 云端翻译 | 15.4 | 1.13 / 2.90 | 2.55 | 1.41 / 3.15 | 1.58 | 33.7 | 2 | 26.5 |
| Qwen 3.1 云端识别 + 云端翻译 | 13.6 | 1.27 / 2.74 | 3.27 | 2.10 / 3.84 | 2.29 | 35.7 | 10 | 1.2 |

\* 不含系统识别服务。分语言的错误率（Apple / SenseVoice / Qwen 3.1）：英 12.9 / 16.9 / 11.1，日 22.4 / 20.0 / 22.8，韩 11.4 / 14.6 / 13.0，中 10.5 / 10.2 / 7.8。同一配置两次跑之间，分语言的错误率会差 1 个点左右。

Qwen 3.1 第一次跑的是 16.9%，被 Tomoru 自己的两个问题拖低，评测找出来后修好了（[`docs/local-asr_zh.md`](../docs/local-asr_zh.md) 的“云端识别”）：

- 没人说话 10 秒就挂断，误伤了音乐：Billie Eilish 的歌，人声检测从头到尾没判出人声，错误率 98.5% → 修后 57%。现在要“没人声、也没声音”才挂断。
- 服务端临时结果末尾的预览会乱加句号，断句器照着提交，同一段话提交两次（“청중들**다우리실적**한테…우리실적이”）：韩语 20.9% → 13.0%。

SenseVoice 原来改写 24%：每 0.4 s 重新解码，前面已经显示的词会来回变。现在只显示连续两次解码一致的部分：改写 2%，上屏晚约 0.5 s（原来 0.64 s），错误率不变（[`docs/local-asr_zh.md`](../docs/local-asr_zh.md)）。

Apple 的延迟（2026-10-17 试过，都没采用）：SpeechTranscriber 大约每 1 s 才出一批字，调分析优先级、把送音频的粒度从 100 ms 改成和系统录音一样的 10 ms，都没有变化。“说完到见译文”几乎全花在等它打出句号定稿上（1.12 s，翻译本身只占 0.03 s）。每次用 9–11 段、每段 2.5 分钟做 A/B：

| 做法 | 收益 | 代价 |
|---|---|---|
| 同时跑 DictationTranscriber（每 0.2–0.3 s 出字），把它多出来的一截接在灰字后面 | 上屏 p50 −0.19 s（0.80 → 0.61） | 改写 4% → 38%（日语 55%：它写假名，SpeechTranscriber 写汉字）。只显示它连续两次一致的部分：改写还是 35%，收益只剩 −0.07 s |
| 一停顿就让 SpeechTranscriber 定稿（中文现在就这样做） | 见译文 −0.3 s，定稿 −1.2 s | 英语错误率 12.9% → 31.3%：提前定稿后模型会写坏后面的话（整句变成“..........”、吞掉半句） |
| 同上，只对韩语（2026-10-20，6 段，新旧同时跑：`vad_ko_off` / `vad_ko_on`） | 见译文 p50 1.07 → 0.69 s，p90 3.22 → 2.38 s；定稿 −1.2 s | 错误率 11.1% → 12.5%，快语速播客 11.3% → 14.8%：切点前后的词被写坏（「집으로 가신 겁니다」→「으로 가 겁니다」、「60번째 주주총회」→「60 번째 14. / 총회.」）；碎行 5% → 8% |
| 按人声检测，静音 0.7 / 1.0 s 就提交，不等文字 1.3 s 不变 | 没有 | 0.7 s 时碎行 8% → 26%：最后几个词比提交晚到 |

长句的切法（2026-10-19 改，`internal/segment/joint.go`）：原来超长时只在逗号处切，英文上限 90 个字母。日韩中途几乎没有逗号，一行会长到一百多字；英文在用户自己保存的字幕里也有三分之一超过两行。现在英文上限改为 60；超过上限 1.2 倍（日韩是 1.5 倍）还没有逗号，就在连接处切：英文切在连词前面，日语切在接续助词后面，韩语切在连接词尾后面。中文不变，由停顿来切。

| 语言 | 长行% | 碎行% | chrF |
|---|---|---|---|
| 英文（新旧同时跑，`seg_en`） | 9 → 1 | 11 → 9 | 27.3 → 26.6 |
| 日语（对比 `apple_cloud`，`seg_ja`） | 7 → 2 | 5 → 6 | 38.2 → 37.5 |
| 韩语（对比 `apple_cloud`，`seg_ko`） | 12 → 1 | 7 → 6 | 19.1 → 19.4 |

- 「见译文」p90 会变长（英文 2.71 → 3.03 s），这是计时方式造成的：它按行算，前半句被切出来时，起点是它自己的最后一个词，而这时后面已经又说了一截。实际上前半句的译文比以前整句一起出要早。
- 门槛和断点是先离线挑的：用人工字幕的断点当标准答案，模拟了几种门槛。1.2 倍对日韩切得太碎，2 倍又几乎不起作用。
- 让 Jev（OpenRouter 上的 `typesafe/jev-1.14`）来选断点，和人工断点的吻合度并不比规则高（准确率 61.3 vs 62.4），而且每次要 1.3–2.1 s，所以没有采用。
